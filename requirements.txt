1. PURPOSE AND CONSTRAINTS
--------------------------
Build a low-latency C++ in-memory limit order book and matching engine as a
portfolio project for trading systems / quant developer roles. Demonstrate
precise exchange-style semantics, data-structure tradeoffs, memory management,
deterministic behavior, testing discipline, and honest performance measurement.

Developer: intermediate C++ experience.
Schedule: 28 work sessions over approximately four weeks, 1–2 hours per day
(28–56 hours total). Day numbers are sequential sessions, not calendar deadlines.
Primary development and measurement platform: macOS, on the developer's machine.
Language/build: C++20 and CMake; repository-local LLVM/Clang 23.1.5 via the
local-llvm presets. Apple Clang 17 remains a supported, verified alternative.
Keep the core portable; Linux validation is optional and must not be claimed
unless performed. Record actual compiler, CMake, OS, and hardware versions.
Use the standard library for the core; keep external dependencies minimal.

Portfolio story: implement a clear baseline, prove its behavior, profile it,
make one evidence-based optimization, and explain the results and limitations.
This is an educational simulator, not a production exchange or trading system.
It has no broker connectivity, live trading, or real-money execution.

2. REQUIRED SCOPE
-----------------
- One instrument, one order book, and one thread owning all mutable book state.
- Buy and sell limit orders with good-till-cancelled (GTC) behavior.
- Add, cancel, and replace commands; execution events and explicit rejections.
- Price priority, then FIFO arrival priority within each price level.
- Partial fills, multi-order matching, and sweeps across multiple price levels.
- Best bid/ask, per-level aggregate quantity, and bounded depth snapshots.
- Deterministic synthetic command generation and replay from a documented file.
- Correctness tests, a simple reference model, and invariant validation.
- A release-mode benchmark executable with reproducible workload definitions.
- One measured optimization, architecture notes, results, and a runnable demo.

Excluded from the four-week core: networking, GUI, concurrent matching, multiple
instruments, market/IOC/FOK/stop/iceberg orders, auctions, fees, risk checks,
persistence/recovery, real exchange feeds, and distributed deployment.
These are stretch ideas only after the core acceptance criteria are met.

3. MATCHING CONTRACT
--------------------
Numeric representation:
- Use explicit integer types: uint64_t order IDs and quantities; int64_t prices
  expressed in ticks. Prices, IDs, and submitted quantities must be positive.
- Floating-point arithmetic must not determine price priority or matching.
- Aggregate quantities and counters need checked bounds; overflow must never
  silently wrap. Reject invalid input before changing book state.

Add:
- Reject invalid side, nonpositive price/quantity, and duplicate live order ID.
- Match a buy while its limit >= best ask; match a sell while limit <= best bid.
- Execute at the resting order's price, oldest order first at that price.
- Emit one trade per resting-order fill with maker ID, taker ID, price, quantity,
  and a deterministic event sequence number (no wall-clock dependency).
- Remove fully filled resting orders and empty price levels immediately.
- Rest any remaining incoming quantity at the back of its own price level.
- IDs are unique among live orders; reuse after removal is allowed. Explain this
  simplified identity rule in the public command-format documentation.

Cancel:
- Cancel the entire remaining quantity of a live order by ID.
- Unknown or already removed IDs produce an explicit rejection and no mutation.

Replace (intentionally simple portfolio semantics):
- Supply the live ID, new limit price, and new remaining quantity; side is fixed.
- Validate all fields and applicable bounds before removing the old order.
- A valid replacement retains its ID but ALWAYS loses time priority, including
  unchanged fields or a size reduction. It behaves as cancel plus a new add,
  can immediately trade, and rests at the back if a remainder exists.
- Unknown IDs or invalid replacements leave the original book unchanged.
- This rule is a project choice, not a claim about all venues' amend policies.

Observability and limits:
- Define stable acknowledgement/rejection/trade event ordering and reason codes
  before implementing replay. Logical input validation failures are recoverable.
- Queries do not mutate state. Empty bid/ask must be represented explicitly.
- Best-to-worst depth output contains price, total remaining quantity, order count.
- Document resource limits and allocation-failure behavior. Do not claim recovery
  from process-level allocation failure unless it is implemented and tested.
- No self-trade prevention: participants/accounts are outside the model.

-----------------------------------
Suggested layout (create incrementally):

  include/order_book/       public types and engine interface
  src/                     book implementation
  apps/                    command-line replay/demo
  tests/                   unit, invariant, and differential tests
  benchmarks/              workload generator and benchmark executable
  data/                    small, deterministic replay examples
  docs/                    architecture, command format, performance methodology
  results/                 small benchmark summaries and environment metadata
  README.md                quick start, project explanation, demo, results links
  requirements.txt         this specification and daily progress record

Baseline design:
- Ordered price maps for each side, FIFO lists per level, and an order-ID lookup
  holding stable handles into those lists. Track aggregate quantity per level.
- Document iterator lifetime, ownership, and removal order. Avoid dangling handles.
- Describe actual complexity: price lookup/insertion is O(log P), ID lookup is
  expected O(1), and FIFO unlink is O(1); removing an empty price level may incur
  additional work. A sweep also scales with the resting orders it fills.
- Keep parsing, formatting, disk I/O, and console output outside the matching core.
- Prefer a small concrete API to inheritance or framework scaffolding.
- Start with readable standard containers; choose an optimization after profiling.
  Candidate work includes reserving the ID index, recycling order storage, or
  reducing allocations. Fixed-capacity designs require explicit exhaustion rules.

Build targets: core library, replay/demo executable, test executable(s), benchmark.
Use CTest as the test entry point. Enable warnings in development and support
AddressSanitizer/UndefinedBehaviorSanitizer builds separately from benchmarks.
Do not commit build products or large generated workloads.

Code documentation requirement (applies throughout the project):
- Comment overall logic, invariants, ownership/lifetime, and non-obvious decisions
  in code. Explain why an algorithm or validation rule exists where useful.
- Do not comment every line or paraphrase obvious syntax. Keep comments accurate
  as implementation changes; document public behavior in the API and docs.
- Apply the same standard to tests and build scripts when their logic needs context.

5. CORRECTNESS AND PERFORMANCE ACCEPTANCE CRITERIA
------------------------------------------------
Correctness gate:
- Tests cover FIFO, both sides, crossing/non-crossing orders, partial/full fills,
  sweeps, empty-level cleanup, cancellation positions, replacement priority and
  crossing behavior, invalid input, ID reuse, duplicates, and numeric boundaries.
- Book invariants hold after each command in test runs: no crossed resting book;
  no empty levels; positive live quantities; correct aggregate totals; consistent
  side/price and ID index; each live order appears exactly once.
- Quantity conservation is checked for fills and residuals; explicit cancellation
  and replacement changes are accounted for separately.
- Compare events and canonical book state against a deliberately simple independent
  reference model over seeded randomized streams, including invalid commands.
- Replay of identical input produces identical events and final state.
- Tests pass in normal and supported sanitizer builds with no reported issues.

Benchmark methodology:
- Benchmark engine operations on pre-generated commands; exclude parsing, file I/O,
  console output, and workload generation from timed regions. Consume/check results
  so the compiler cannot discard the workload. Account for event emission costs.
- Use a monotonic clock (e.g. std::chrono::steady_clock); report clock/timing overhead.
  Separate per-command latency sampling from batched throughput measurements.
- Report operation counts, throughput (commands/s), and p50/p95/p99/max latency in
  ns/command. Explain that a command can generate several trades; also count fills.
- Cover passive adds, cancels, replacements, aggressive matches, and multi-level
  sweeps. Report per-operation latency as well as any mixed-workload summary.
- Specify seed, command proportions, price distribution, initial live orders,
  price levels, maximum occupancy, fill/rejection counts, and data-set size.
- Include at least two book sizes (initial targets: 1,000 and 10,000 live orders).
  Mixed steady-state workloads should replenish drained liquidity and report the
  actual occupancy range; do not label an ever-growing book as steady state.
- Warm up first; reset each measured run to the same initial state. Use at least
  five measured repetitions, reporting variation and the quantile calculation.
- Record commit/build identity, optimization flags, hardware/chip, macOS version,
  compiler, power mode, and relevant background activity. Run without sanitizers.
- macOS scheduling and timer noise limit conclusions; do not claim hard real-time
  guarantees, nanosecond precision, Linux CPU pinning, or exchange-level latency.

Performance goal:
- Establish the baseline before setting an absolute latency target. No unsupported
  sub-microsecond claim is required for project success.
- Aim for >=10% improvement in median throughput or p99 latency on one preselected
  workload, with unchanged correctness and disclosed effects on other workloads.
  This is an experimental target, not a mandatory outcome: if the change does not
  exceed run-to-run noise, report that and retain the clearer implementation.
- Preserve comparable baseline/optimized results and explain the cost or tradeoff.
